El checklist del revisor: qué mirar más allá del diff

Cuando abres una pull request en GitHub, GitLab o Bitbucket, lo primero que ves es una lista de archivos modificados. La tentación de iniciar por el diff es irresistible. El hábito distingue a un revisor mediano de uno excelente: empieza por el contexto. Lee la issue vinculada, los comentarios del ticket y la descripción del PR. Si falta ese enlace, es la primera señal de alarma.

Una revisión efectiva tiene un ritmo concreto. La investigación interna de Google y Microsoft muestra que la capacidad de detectar defectos cae de forma dramática cuando el PR supera las 400 líneas de cambios y cuando el revisor procesa más de 500 líneas por hora. Si el cambio es enorme, no intentes tragarlo de una vez. Divide la revisión por commits o pide al autor que fragmente el trabajo.

El orden sugerido:

- Lógica de negocio: ¿cubre los casos de frontera? Piensa en entradas vacías, fechas límite, husos horarios y valores negativos.

- Seguridad: ¿hay datos confiables? Busca interpolación de strings en consultas SQL, uso de `eval`, secretos incrustados y ausencia de validación de permisos.

- Rendimiento: ¿hay consultas N+1, bucles anidados sobre colecciones grandes o trabajo repetido dentro de un `for`?

- Mantenibilidad: ¿nombres honestos, funciones pequeñas, ausencia de efectos colaterales ocultos?

Un caso típico: en una pasada reciente, un desarrollador cambió la función de parseo de fechas para soportar el formato ISO 8601. El diff era limpio, pero la función original consideraba la zona horaria local y la nueva devolvía `UTC` silenciosamente. Ningún test lo detectó porque los casos usaban la misma zona. El revisor que preguntó «¿qué pasa si el servidor corre en otra región?» salvó una madrugada de incidentes.

Prompt
Actúa como un revisor senior de código [lenguaje o framework]. Revisa este diff: [pega tu código]. Identifica problemas de lógica de negocio, seguridad, rendimiento y mantenibilidad. Clasifica cada hallazgo por severidad (bloqueante, mayor, menor) y propón una solución concreta para cada uno.

Cómo escribir comentarios que el equipo acepta de buena gana

El PR genera un diálogo. La manera de redactar ese diálogo decide si el autor corrige el código o se defiende. Un comentario como «esto está mal» provoca cortisol, no colaboración. El formato *conventional comments* —proyecto abierto con vocabulario específico— ofrece una alternativa eficaz. Prefijos como `suggestion:`, `question:`, `issue:` y `nitpick:` comunican la intención del comentario y su impacto real. Además, si el autor puede responder con una acción concreta, la iteración se acorta.

Dos versiones del mismo hallazgo:

Versión A: «No uses `map` para esto, es confuso.»

Versión B: `suggestion:` Podríamos sustituir este `map` por un `for...of` explícito, porque aquí el retorno temprano dificulta seguir el flujo. ¿Te parece que lo cambiamos?

La segunda versión explica el *porqué*, propone una alteración experimental y deja la decisión en manos del autor. El tono importa tanto como el argumento técnico. Un revisor excelente no escribe para sentar cátedra; escribe para que el equipo aprenda.

Los comentarios deben llegar a tiempo. Una revisión que tarda tres días en responder tiene menos valor que una de quince minutos al día siguiente. El contexto se enfría, el autor cambia de tarea y el coste de recuperar el hilo supera el beneficio del hallazgo. Si el PR supera las 24 horas en cola, programa una sesión síncrona breve.

Prompt
Tengo este comentario de revisión que quiero mejorar: [comentario original]. Reescríbelo usando el formato Conventional Comments y un tono colaborativo. El contexto es [archivo o módulo revisado]. Preserva la intención principal, que es [impacto esperado del cambio]. Si es necesario, divide el comentario en dos: uno para la cuestión técnica y otro para la preferencia de estilo.

La revisión asistida por IA: el tercer ojo que ya existe

En 2026, las herramientas de IA generativa no son una promesa; son parte del flujo diario. GPT-5, Claude 4.5 Sonnet y Gemini 2.0 pueden leer un diff completo, detectar olvidos evidentes y proponer casos de prueba. Un flujo de trabajo asequible: el CI ejecuta el linter y el análisis estático (SonarQube o Semgrep), un bot de IA genera una primera pasada de comentarios y el revisor humano se concentra en lo que la máquina no puede evaluar: el contexto de negocio, la historia de la deuda técnica y las decisiones de arquitectura.

El peligro silencioso es la confianza ciega. Diversos estudios sobre automatización muestran el fenómeno de la "ceguera inducida por automatización": cuando el sistema dice que todo está bien, la atención humana decae. El bot reduce la carga de revisión, pero no elimina la responsabilidad. El revisor debe firmar con su nombre la aprobación, sabiendo que el criterio final es suyo.

Una estrategia práctica: pide a la IA que genere una lista de preguntas, no una lista de sentencias. Las preguntas orientadas a casos de borde (concurrencia, estados vacíos, formatos externos) amplían la cobertura de la revisión humana. Después, contrasta las respuestas del autor contra el código real. La IA acelera la exploración, pero la validación sigue siendo humana.

Prompt
Actúa como mentora de revisión de código. Dame un plan de revisión para este PR: [descripción o enlace]. Primero, sugiere tres preguntas de contexto que debería hacerle al autor. Después, para cada archivo modificado, indica qué riesgos buscar (seguridad, concurrencia, compatibilidad con [versión o plataforma]). Cierra con tres casos de prueba que debería pedir antes de aprobar.

Errores comunes al revisar pull requests (y cómo esquivarlos)

El primer error es revisar por encima y aprobar con un emoji. La cortesía mata la calidad. Si no hay un solo comentario en un PR de 300 líneas, revisa de nuevo. Un segundo vistazo rara vez devuelve cero hallazgos.

El segundo es la guerra de gustos personales. Discutir si las llaves van en la misma línea o si el nombre de una variable es «mejor» solo retrasa el código. Distingue entre preferencia (sometida a la guía de estilo) y problema real (comportamiento incorrecto, riesgo de seguridad, complejidad innecesaria).

El tercero, quizás el más doloroso, es la parálisis prolongada. Un PR que lleva más de dos días en revisión genera ansiedad y bloquea la integración. Si ocurre, convoquen una sesión conjunta de quince minutos con el autor y decidan en vivo: se corrigen los puntos críticos y se registran los pendientes como items de mejora futura.

El cuarto error afecta a las relaciones: comentar sobre la persona en lugar de sobre el código. Frases como «no entendiste el requisito» atribuyen intención y provocan defensas. Reformula: «el requisito de [X] parece no cubierto; ¿podemos revisarlo?». El código es el interlocutor; la persona, la aliada.

El quinto es ignorar las pruebas. Pedir tests para los casos de borde detectados es tan valioso como señalar el bug. Un revisor que aprueba sin tests introduce una bomba de relojería para el siguiente refactor.

Prompt
He detectado estos problemas en mi flujo de revisión: [lista de problemas]. Actúa como entrenador de ingeniería y propón un plan de 30 días para corregirlos, con acciones semanales concretas, una métrica para medir el progreso y una herramienta que facilite cada hábito. Sé específico y pragmático.
