Mide primero: el perfilador es tu mejor aliado

La regla número uno del rendimiento es no adivinar. Cuando un compañero te diga que la aplicación va lenta, tu primera acción debe ser abrir un perfilador, nunca reescribir código. Las heramientas actuales ofrecen una visibilidad impresionante: py-spy para procesos en producción, cProfile para análisis de escritorio, perf a nivel de sistema y Chrome DevTools para frontend. Cada una responde a una pregunta distinta: ¿dónde se consume CPU? ¿dónde se bloquea la E/S? ¿qué funciones acaparan el tiempo de respuesta?

Un ejemplo real: una API de informes tardaba cuatro segundos en devolver datos. El equipo había añadido índices a la base de datos sin éxito. Al ejecutar cProfile con 500 peticiones reales, el perfilador señaló que el 78 % del tiempo se iba en una función de serialización de fechas dentro de un bucle anidado. Cambiar el formato de fecha a un parseo directo redujo el tiempo a 600 milisegundos. Sin perfilar, jamás lo habríamos encontrado.

Los pasos son siempre los mismos: establece una línea base con métricas concretas (p95, rendimiento, uso de CPU), ejecuta el perfilador en condiciones de producción o lo más parecido posible, examina las funciones más lentas y clasifica los hallazgos por impacto.

Prompt
Actúa como un ingeniero de rendimiento senior. Diseña un plan de perfilado para [lenguaje o framework] en [tipo de aplicación]. Incluye las herramientas exactas de profiling, las métricas que debes capturar antes y después, y un método para interpretar el resultado e identificar el cuello de botella principal.

La caché: la herramienta que nadie sabe configurar bien

La caché reduce la latencia, pero también reduce la factura del servidor. Un informe generado durante tres segundos que se consulta cada minuto por cincuenta usuarios genera cincuenta procesos de cálculo. Si cacheas el resultado durante 60 segundos, el trabajo se reduce a una única ejecución y cuarenta y nueve lecturas a memoria. El ahorro es del 98 %.

La clave está en elegir la capa correcta. Una implementación llamada cache-aside funciona así: la aplicación consulta primero la caché; si hay un acierto, devuelve el dato; si hay un fallo, lee la base de datos, guarda el resultado en caché y lo devuelve. Para sistemas distribuidos, Redis sigue siendo el estándar en 2026, aunque el cliente se conecte a través de un gestor de tráfico. Los TTL deben definirse según la tolerancia del negocio a datos obsoletos: una página de precios admite cinco minutos, un saldo bancario quizá solo unos segundos.

El error más habitual en este punto es cachear de más. He visto equipos almacenando en Redis objetos de sesión, datos personales y contraseñas temporales sin cifrar. La caché no debe contener información sensible sin un control de acceso riguroso ni datos que cambian cada milisegundo, porque acabarás manteniendo dos estados idénticos que se desincronizan.

Señala además qué datos no deberían cachearse.

Consultas a base de datos: el cuello de botella silencioso

Las bases de datos acaparan la mayoría de los problemas de rendimiento en aplicaciones empresariales. El sospechoso habitual es el problema N+1: una consulta que carga una lista de clientes y, para cada cliente, ejecuta otra consulta para obtener sus facturas. Con trescientos clientes, eso equivale a trescientas una consultas. Los ORM modernos lo facilitan sin darte cuenta: Django, Hibernate y Entity Framework ofrecen mecanismos de precarga como select_related o Include, pero hay que aplicarlos de forma consciente.

La solución incluye tres pasos. Primero, revisa el registro de consultas y busca patrones repetitivos; la mayoría de los ORM registran las consultas SQL, y herramientas como Django Debug Toolbar o el panel de Hibernate los muestran en tiempo real. Segundo, usa la precarga para convertir consultas N+1 en dos o tres consultas con JOIN y un solo viaje a la base de datos. Tercero, analiza el plan de ejecución con EXPLAIN y presta atención a los escaneos secuenciales. Si una tabla con dos millones de filas se recorre entera cada vez, un índice cubriente puede reducir el tiempo de consulta de segundos a milisegundos.

Otro punto crítico es la paginación. Los tipos OFFSET se vuelven lentos en tablas grandes porque la base de datos descarta muchas filas; la paginación por cursor, basada en un valor único de la última fila devuelta, es constante en tiempo y se mantiene estable incluso cuando los datos cambian entre peticiones.

Prompt
Elabora una auditoría de rendimiento de base de datos para [proyecto o aplicacion]. Genera una lista de las consultas más pesadas, identifica problemas N+1, recomienda índices concretos y escribe un guión de EXPLAIN para detectar escaneos secuenciales. Finaliza con una política de paginación por cursor.

---

Errores comunes que arruinan la optimización

El primer error es optimizar sin medir. He visto características "optimizadas" que empeoraban el rendimiento porque se basaban en una intuición equivocada. Nunca modifiques código que no has perfilado. El segundo error es confundir microoptimizaciones con mejoras reales: cambiar una variable de local por inline en JavaScript ahorra nanosegundos, mientras que eliminar una consulta N+1 ahorra segundos. Prioriza siempre el impacto.

El tercero es no observar producción. Un perfilador de escritorio no refleja la competencia real por CPU, las conexiones de red o la contención de recursos. Herramientas como Prometheus y Grafana miden latencia, errores y saturación en tiempo real. La métrica que debes vigilar es el percentil 95, porque representa la experiencia de los usuarios en condiciones adversas, no al usuario afortunado que responde en 10 ms.

El cuarto error consiste en sobrecargar la base de datos con índices redundantes. Cada índice acelera la lectura pero ralentiza la escritura y consume almacenamiento. Antes de añadir un índice, pregúntate si una consulta concreta lo necesita y si ya existe uno compuesto que lo cubra. Al final, el rendimiento no se logra con trucos aislados sino con un ciclo de medición, cambio y validación.

Prompt
Redacta una lista de verificación con errores comunes de optimización en [lenguaje o plataforma]. Para cada error, indica la señal de alerta que delata su presencia, el impacto en producción y una corrección concreta. Formato de salida: tabla en texto con columnas Error, Señal, Impacto, Solución.
